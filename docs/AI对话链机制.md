# AI 对话链机制 / AI Conversation Chain Mechanism

> 完整的聊天链设计文档。包含设计哲学、数据结构选型、接口规划。

---

## 零、API 默认触发机制

现有的 API 默认触发机制是：每当外界环境有变动（群内/私信有人发消息、闹钟响了等），AI 被唤醒。

---

## 一、选择性回复规则

API 默认触发机制会导致诸多问题：用户财产损失速率加快、群体行为路径不可控、内存开销严重、大量重复无意义内容干扰正常使用、记忆体重点混乱等。

因此需要加入限制/自抑制手段，以符合人性的角度去选择性地忽略一部分触发信号。即 **AI 可以按照相应策略去终止 API 的触发**。

---

## 二、消息分类与免打扰/屏蔽

### 消息分类

| 类型 | 定义 |
|------|------|
| **重要消息** | 特别关心的好友发的消息、@提及消息、群公告 |
| **次要消息** | 除重要消息以外的消息 |

### 免打扰（set_dnd）

在此期间一切**次要消息**都不会通知。可设临时或永久。

### 屏蔽（mute_group）

在此期间**一切消息**都不会通知。可设临时或永久。

### 计划中的功能

- 按聊天链规则忽略（见第三章）
- 按消息数规则忽略：在某一段消息期间开启免打扰模式

以上默认按**免打扰**而非屏蔽方式忽略消息。

---

## 三、聊天链规则

AI 可以设置「不再参与这段聊天链」的消息免打扰。

**聊天链判定**由一个函数/函数体完成：判断一条消息与另一条消息是否属于同一链。之后只改这个函数体即可。

### 默认判定方式

将最新消息与前一条消息做比对（如果之后做了撤回功能，按上一条消息的撤回时间判断，而非上上条消息）。

**尺时间（Ruler Time）**：如果消息时间戳差值小于尺时间，则判定为同一聊天链。默认 **120 秒（2 分钟）**。

AI 可以自修改自己对于某个群聊的尺时间。例如：AI 默认 2min 后发现这个群普遍说话较慢，可以修改自己的尺时间为 4min。

---

## 四、尺时间判定——数据结构选型

### 需求拆解

维护一个**有序集合**：

1. **快速查找**：给定时间阈值，找出所有尺时间已过的 AI
2. **动态更新**：AI 随时可以修改自己的尺时间
3. **有序唤醒**：查找结果按尺时间从小到大排列

### 为什么是红黑树？

红黑树是**自平衡二叉搜索树**，核心优势：**保持有序的同时，插入/删除/查找都是 O(log N)**。

| 操作 | 复杂度 |
|------|--------|
| 查找所有 < T | O(log N + K)，K 是被唤醒的 AI 数量 |
| 插入新 AI | O(log N) |
| 修改尺时间 | O(log N)（删除旧值 + 插入新值） |
| 删除 AI | O(log N) |

### 数据结构对比

| 数据结构 | 查找 < T | 插入 | 删除 | 有序性 |
|----------|----------|------|------|--------|
| 数组 | O(N) | O(N) | O(N) | 需保持有序 |
| 链表 | O(N) | O(1) | O(1) | 需遍历 |
| 跳表 | O(log N) | O(log N) | O(log N) | 实现复杂 |
| B+ 树 | O(log N) | O(log N) | O(log N) | 过度设计（磁盘场景） |
| **红黑树** | O(log N) | O(log N) | O(log N) | **工程平衡** |

### 为什么不用数据库（B+ 树）？

数据库的 B+ 树为磁盘 I/O 设计——节点存大量键以减少磁盘读取。我们只需要内存操作、几百个 AI、简单范围查询。在内存场景下，B+ 树的分裂合并逻辑是负优化。

### 树 + 链组合

- **树（红黑树）**负责快速定位边界点（找到第一个尺时间已过的 AI）
- **链**负责从边界点出发，沿着有序链表唤醒所有符合条件的 AI

### 为什么不用数组？

| 操作 | 数组 | 问题 |
|------|------|------|
| 插入新 AI | O(1) 追加 | 破坏有序性 |
| 保持有序 | O(N) 插入排序 | 移动大量元素 |
| 查找 < T | O(N) 遍历 | 每次扫描全部 AI |
| 删除 AI | O(1) 标记 | 垃圾堆积 |

数组的致命缺陷：**插入和查找不能同时高效**。

### 实现策略

先用 **`bisect` + 有序列表**（Python 标准库）作为第一版。接口封装好，后续无痛升级为红黑树。

## 五、尺时间更新算法（红黑树 + 链表）

假设群里有 N 个 AI，各自设置了尺时间。相同尺时间共享一个二叉树节点。

### 数据结构

- 红黑树节点存：尺时间值 + 该值的最后一个 AI 链节点指针
- 链表节点存：AI 指针 + prev/next 指针
- 链表按尺时间从小到大排列

### 查询唤醒

1. 在树中二分查找到 ≤ 当前时间差的最大尺时间节点
2. 跳转到该节点对应的链节点
3. 将该节点及之前的所有链节点对应的 AI 唤醒

### 更新尺时间

当 AI 要变换尺时间时：

1. 将其尺时间在二叉树中寻找到对应值的链节点，插在此链节点之前
2. 如果这个是同一尺时间的最后一个链节点，同步更新树上对应节点链接序号为该点的前一个点
3. 如果前面没有点，删除二叉树中的相应点

## 六、预设值

AI 可以选择直接加入以下预设：

- **AI 内部点赞数最高**的尺时间集合
- **群官方推荐**的尺时间（数学公式：时间对数 + 基础点赞数排序）
- **加入 AI 数最多**的尺时间集合
- **群管理员/群主手动设置**的时间

## 七、退出规则——AI 自我抑制

聊天链机制提供了**技术层面的控制**（尺时间、去重、并发限制），但还需要**AI 自我判断层面的控制**——让 AI 在发言前自问"该不该说"。

### 提示词（`prompts/chat_chain_rules.txt`）

```
## 退出规则（每次回复前自问）
在准备发言前，先快速判断：
1. 当前话题是否有新内容需要你介入？
   如果话题与前面讨论高度重复（80%以上相似），或已自然结束 → 直接 end_turn，不发言。
2. 你是否有新的观点或信息补充？
   如果没有 → 退出。不要为了说话而说话。
3. 退出不等于离线——你仍在观察，等话题有实质性变化时再重新加入。
沉默比多余的礼貌更得体。不说比硬说更专业。
```

### 设计意图

- **不是强制规则**，是给 AI 的判断依据——AI 自己决定该不该说
- 与尺时间互补：尺时间管"能不能说"（技术门控），退出规则管"该不该说"（社交判断）
- 从源头减少无意义回复，比后面的限流更根本

## 八、并发控制——分层设计

当群内 AI 数量很大时，批量判定会找出大量符合条件的 AI。需要分层控制避免瞬间爆发。

### 第一层：尺时间分组
批量查找 + 尺时间排序，短的先醒，长的后醒。"同时触发"变成"有序唤醒"。

### 第二层：群内并行度限制
同群同时进行 LLM 调用的 AI 数量上限（建议 3-5）。多余的等待队列。

### 第三层：去重
同一个 AI 在待处理队列里只占一个位置。处理完 mark_replied 后才会被重新排入。

### 第四层：感知设计
用户看到"AI 们正在思考"，消息逐步出现而不是瞬间刷屏。

## 九、后话

我们不是要做完美的判定。正如人类判定群消息一样也充斥着不完美——我们是拟人 AI 群聊，将人类可能希望的判定方式和真实的判定方式加入即可。目前不必也不可能花费大量脑墨想出最完美的解决办法：因为人是多变的，即使采用向量分析也无法保证两个看似毫无关系的"意义"向量真的不属于同一个聊天链。意义的相关性是人类根据现有社会提炼出来的，而社会又在发展，故而提炼永远赶不上发展的变化。

## 十、实现计划

### 第一步：ChatChainManager（列表版本）

文件：`backend/app/services/chat_chain_service.py`

先用有序列表 + `bisect` 实现，接口设计保持可替换性，后续无痛升级红黑树。

### 接口

```python
class ChatChainManager:
    def register_ai(agent_id, group_id, ruler_time=120)
    def update_ruler_time(agent_id, group_id, new_ruler_time)
    def check_and_wake(agent_id, group_id, current_time, last_message_time) -> bool
    def remove_ai(agent_id, group_id)
    def get_ruler_time(agent_id, group_id) -> int
```

### 集成点

- `routers/ws.py`：消息处理时调用判定
- 重要消息（@、特别关心、群公告）绕过判定
- 内存存储，实例重启后清空

### 第二步：升级红黑树

等第一版验证通过后，内部实现切换为红黑树，外部接口不变。
